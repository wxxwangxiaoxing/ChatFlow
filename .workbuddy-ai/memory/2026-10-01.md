## 通读 IM 即时聊天系统（ChatFlow）需求与架构文档

- 工作区当前**只有两份文档、无任何代码**：
  - `IM即时聊天系统需求文档.md` — PRD V1.0，16 章（角色权限、功能需求 P0/P1/P2、关键流程、NFR、安全合规、数据模型、里程碑、风险、验收 DoD）
  - `IM总体架构设计文档.md` — 架构 V1.0，25 章（分层视图、接入/消息/同步/群组/Presence/推送、数据架构、部署容灾、安全、可观测、容量规划、ADR）
- 项目定位：可私有化部署的企业级 IM（代号 ChatFlow），对内是员工统一沟通入口，对下是业务系统统一消息底座（OpenAPI / Webhook / 机器人 / 消息卡片），对外部联系人为二期。
- 核心目标：消息**不丢、不重、不乱序**；送达率 ≥99.99%；同城单聊 P95 ≤200ms / P99 ≤500ms；核心可用性 99.95%；100 万 DAU、50 万并发连接、单群 5000 人。

### 核心机制（理解项目的关键）
- **幂等**：客户端生成 `clientMsgId`，Redis SETNX(TTL 5min) 预占 + MySQL 唯一索引兜底。
- **发号**：会话级 `Seq`，Redis `INCR conv:seq:{convId}`，批量预取步长 1000，落库兜底、宕机不回退。
- **存储先行再 ACK**：写 Kafka(acks=all，分区键=convId 保证分区内有序)即回 ACK，异步落库，失败靠消费者重试 + 死信告警 + 对账任务兜底。
- **多端同步**：账号级 `SyncKey` 版本号 + `sync_log`（按 user 分片、保留 7 天）增量拉取；已读水位 `lastReadSeq` **只进不退**，变更事件在线广播，目标 ≤2s 一致。
- **群扇出**：读写扩散混合，≤200 人写扩散（每人收件箱）、>200 人读扩散（群消息表单副本，成员按 Seq 拉）；`join_seq` 保证新成员看不到入群前历史消息；FanoutService 按 64 片并行。
- **Presence**：Redis TTL 承载在线态 + 5s 批量聚合上报 + 200ms 窗口防抖广播，**不写主库**，故障时降级为 unknown 且不影响收发。
- **端上 Outbox**：本地先入库展示"发送中"（乐观 UI），指数退避重试 1/2/4/8/16s 最多 5 次，超限标红。

### 数据与部署
- 分片：消息 `hash(conv_id)%16` 库 × `%256` 表 + 按月分区；会话 `hash(user_id)%8` 库 × `%64` 表。任何查询必须带分片键，跨分片聚合走 ES/ClickHouse。
- 存储选型：MySQL 8.0 + ShardingSphere、Redis Cluster、Kafka、Elasticsearch(IK)、S3 兼容对象存储 + CDN、ClickHouse、Nacos、K8s。
- 语言栈：Go（网关/消息链路）+ Java（业务/后台），gRPC + Protobuf over WSS。
- 部署：两地三中心，核心 SLA 99.95%，RPO ≤1min / RTO ≤5min；金丝雀 + 一键回滚 ≤5min。
- 缓存三层：L1 客户端本地库 / L2 Caffeine 本地缓存 / L3 Redis。

### 已定架构决策（ADR 001–008）
Kafka 先行异步落库｜会话级 Seq 而非全局 ID｜群消息读写扩散混合｜SyncKey 增量同步｜Presence 不落主库｜音视频 WebRTC+SFU（自建 vs 采购待定）｜平台加密为主、E2EE 作租户级可选开关｜端上 Outbox 本地先行。

### ⚠️ 写 DDL 时发现的 4 处设计文档缺陷（已在新脚本中修正，文档待同步修订）
- **偏差 A：`im_message` 不能按月分区**。MySQL 分区表要求**每个唯一索引都包含分区表达式中的全部列**。按月分区（分区键 created_at）后，`uk_conv_seq(conv_id,seq)` 与 `uk_client_msg(sender_id,client_msg_id)` 均不含 created_at → 建表报错 `ERROR 1503`。取舍：保留唯一约束（幂等与顺序是核心），取消分区；数据量由 conv_id 分片承担。备选方案（分区键改 conv_id 的 HASH 分区）仍要求 uk_client_msg 含 conv_id，不推荐。
- **偏差 B：`im_sync_log` / `im_audit_log` 同样冲突**。处理：主键改 `(id, created_at)`（雪花 id 单独即唯一，不损失唯一性）；`im_sync_log` 的 `UNIQUE (user_id, sync_key)` **降级为普通索引** `idx_user_key`（sync_key 由服务端单点单调发号，逻辑上不可能冲突；DROP PARTITION 秒级清理 7 天数据的收益更大）。**影响：数据库文档第 19 章"骨架索引"第 ⑤ 项需相应修订。**
- **偏差 C：`im_conversation` 分片键应由 user_id 改为 conv_id**。文档把 im_conversation 与 member/watermark/draft 一起归为"按 user_id 分片"，但 im_conversation 是"每会话一行"实体表，单聊 conv_id 由双方 uid 哈希生成——按 user_id 分片会导致同一会话在 A/B 视角落到不同分片，无法确定读取目标。原则：分片键由查询条件决定，会话实体永远以 conv_id 查询。
- **偏差 D：分片路由公式有容量浪费**。文档 `dbIndex = hash % 16` + `tableIndex = hash % 256` 会导致 `tableIndex % 16 == dbIndex` 恒成立，即 4096 个 (库,表) 组合中只有 256 个被使用，相当于只实现 1/16 容量。修正为 `h = hash % 4096; dbIndex = h / 256; tableIndex = h % 256`。会话域同理（512 槽位）。
